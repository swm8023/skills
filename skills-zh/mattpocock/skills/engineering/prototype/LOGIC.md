# Logic Prototype

一份自包含 HTML 文件（**shareable demo**），让任何人通过按钮操作状态模型。用于 **业务逻辑、状态转换或数据形状** 的问题：纸上看似合理，走过真实场景才发现不对的事情。

它只有一个文件，无需安装，所以可以交给非开发者（设计师、PM、领域专家），让他们亲自感受模型。因此它使用他们的语言，而不是代码的语言。

## When this is the right shape

- “我不确定这个状态机能否处理先 X 再 Y 的边界情况。”
- “这个数据模型真的能表示这样的场景吗……”
- “写 API 之前，我想先感受一下它应该是什么样。”
- 任何希望 **按按钮并观察状态变化** 的情况。

如果问题是“应该长什么样”，本分支不适用。使用 [UI.md](UI.md)。

## Process

### 1. State the question

写代码前，记录正在验证的状态模型和问题。在 demo 顶部用一段可见介绍说明，不只是注释。回答错问题的逻辑 prototype 完全是浪费，所以明确写出问题，供用户当前观察或 AFK 后回来时核对。

### 2. Isolate the logic in a portable module

把实际逻辑（回答问题的部分）放在一个 `<script>` block 中，写成小型纯 module，以后能直接提取到真实代码库。外围页面是临时的，这个 module 不是。

合适的形状取决于问题：

- **纯 reducer**：`(state, action) => state`。动作是离散事件、状态是单个值时适合。
- **状态机**：明确状态与转换。“现在哪些动作合法”也是问题的一部分时适合。
- 在简单数据类型上运行的 **一组小型纯函数**。没有隐含当前状态、只有转换时适合。
- 当逻辑确实持有持续内部状态时，使用 **方法表面清晰的类或 module**。

选择最符合问题的形状，*不是*最容易接到页面的形状。保持纯粹：不使用 DOM、`document`，按钮 handler 不探入内部。页面调用它，反向没有流动。这样 prototype 才能在自身使命结束后继续有用：问题得到回答后，验证过的 reducer / 状态机 / 函数组能独立进入真实 module。

### 3. Build the shareable HTML file

一个文件，纯 HTML/CSS/JS：不用 framework、bundler、server，全部内联，双击打开，通过邮件转发也能用。任何人打开就应该能运行。

面向非开发者编写。所有标签使用 **domain language**，而不是代码语言：按钮和状态像业务描述，而不是 reducer。用简单话说明发生了什么。

从上到下建立清楚层次：

1. **标题和一句解释**，说明 demo 能探索什么（步骤 1 的问题）。
2. **当前状态**：全部相关状态渲染为易读面板（带标签字段，而非原始 JSON），每次点击后重新渲染，变化可见。必要时标出刚改变的内容，帮助非开发者理解。
3. **自由操作按钮**：每个 action 一个按钮，始终可用，让任何人按任意顺序探索模型。每次点击 dispatch action 并重新渲染状态。
4. **引导 walkthrough**：一组 **scenario**，每个标签页一个。每页简要说明场景（初始情况及观察重点），下方列出该场景按顺序**应点击的按钮**。每步是真按钮：点击执行 action 并进入下一步。启动 walkthrough 时重置为已知初始状态，让每次场景运行一致。

选择能展示棘手情况的场景，也就是纸上难以推演的情况：正常路径、难处理的边界、尝试本应非法的动作。

漂亮但克制：干净排版、宽裕间距、一种强调色。不加动画或花招，任何东西都不要与状态和按钮争夺注意力。

### 4. Hand it over

把文件交给他们，或帮他们打开。他们会在有空时走 walkthrough 和自由操作；有价值的时刻是他们说“等等，这不应该能做”或“咦，我以为 X 不一样”。这些是_想法_里的 bug，正是目标。需要新 action 或场景时就加；prototype 会演化。

### 5. Capture the answer and the prototype

prototype 回答问题后，先保存答案，再按 [SKILL](SKILL.md) 的方式保存 prototype。逻辑分支的对应关系：验证后的 reducer / 状态机 / 函数组进入真实 module（吸收决策）；HTML 外壳随 prototype 进入临时 branch，作为 primary source。它是一个自包含文件，因此在那里仍然很容易重跑。

## Anti-patterns

- **不要添加测试。** 需要测试的 prototype 已不再是 prototype。
- **不要接真实数据库。** 除非问题专门涉及持久化，否则用内存状态。
- **不要泛化。** 不考虑“以后要支持 X 怎么办”。prototype 只回答一个问题。
- **不要混合逻辑和页面。** 纯 module 引用 DOM、`document` 或按钮 handler 后就无法独立提取。页面保持为纯 module 的薄外壳。
- **不要用 framework、bundler 或 server。** 接收者双击一个文件；React app 或 dev server 会破坏“shareable”。
- **不要将 HTML 外壳发布到生产。** 页面为人工点击探索优化，值得保留的是背后的逻辑 module。
