# Triage

通过小型 triage 角色状态机，推进项目 issue tracker 上的 issue。

如果仓库把外部 PR 也当作请求入口（见 issue-tracker 配置），triage 同样覆盖它们：**PR 就是附带代码的 issue**，使用相同角色、状态和状态机，差异在下文标注“for a PR”。按 tracker 配置将裸 `#42` 解析为 issue 或 PR。

triage 期间发到 issue tracker 的每条 comment 或 issue **必须**以以下免责声明开头：

```
> *This was generated by AI during triage.*
```

## Reference docs

- [AGENT-BRIEF.md](AGENT-BRIEF.md)：如何编写耐久的 agent brief
- [OUT-OF-SCOPE.md](OUT-OF-SCOPE.md)：`.out-of-scope/` 知识库如何工作

## Roles

两个 **category** 角色：

- `bug`：某事损坏
- `enhancement`：新功能或改进

五个 **state** 角色：

- `needs-triage`：需要维护者评估
- `needs-info`：等待报告者补充信息
- `ready-for-agent`：规格完整，可交给 AFK agent
- `ready-for-human`：需要人工实施
- `wontfix`：不会采取行动

对 PR，同样的状态针对附带代码解释：`ready-for-agent` 意味着已附 brief，agent 应对 diff 执行下一步；`ready-for-human` 意味着可以由人合并。

每个已 triage 的 issue 应恰有一个 category 角色和一个 state 角色。state 冲突时，先指出并询问维护者，再做任何其他事。

这些是规范角色名，tracker 的实际标签字符串可能不同。映射应已提供给你；没有时，告诉用户运行 `/setup-matt-pocock-skills`。

状态转换：未标记 issue 通常先到 `needs-triage`，再转到 `needs-info`、`ready-for-agent`、`ready-for-human` 或 `wontfix`。报告者回复后，`needs-info` 回到 `needs-triage`。维护者随时可覆盖；发现异常转换，先指出并询问。

## Invocation

维护者调用 `/triage`，用自然语言描述需求。理解并执行，例如：

- “展示所有需要我关注的项”
- “看看 #42”（issue 或 PR）
- “把 #42 移到 ready-for-agent”
- “哪些项可以交给 agent？”

## Show what needs attention

查询 issue tracker，以最早优先展示三类：

1. **Unlabeled**：从未 triage。
2. **`needs-triage`**：正在评估。
3. **`needs-info` 且报告者在最近 triage 笔记后有活动**：需要重新评估。

PR 属于 scope 时，这三类也包含外部 PR，每行标 `[PR]` 或 `[issue]`。发现阶段只展示*外部* PR（tracker 配置定义谁属于外部），协作者进行中的 PR 不是 triage 工作。筛选只适用于发现；用户明确指定的 PR，无论作者是谁都 triage。

展示数量及每项一句概述，让维护者选择。

## Triage a specific issue or PR

1. **Gather context。** 阅读完整 issue 或 PR（正文、comment、label、作者、日期；PR 还要读 diff）。解析已有 triage 笔记，避免重复询问已解决问题。使用项目领域术语探索代码库，并遵守区域 ADR。做两项检查：(a) **redundancy**：按领域概念搜索请求行为是否已有实现，而非只按请求措辞；说明查过哪里。找到后属于已实现的 `wontfix`（步骤 5）。(b) **prior rejection**：阅读 `.out-of-scope/*.md`，指出相似的旧请求。

2. **Recommend。** 告诉维护者建议的 category 和 state、理由，以及相关代码库简述（包括是否已实现）。等待指示。

3. **Verify the claim。** 任何访谈前先核实说法。bug 按报告者步骤复现；PR 验证 diff 是否做到声称内容：checkout，运行相关测试或命令。报告结果：确认（附代码路径）、失败或细节不足（强烈提示 `needs-info`）。已确认的验证让 agent brief 更有力。

4. **Grill（必要时）。** 请求需完善时，分别调用两次 Skill 工具加载 "grilling" 和 "domain-modeling"，逐轮追问，打磨领域术语，并在决策确定时立即更新 `GLOSSARY.md`/ADR。

5. **应用结果：**
   - `ready-for-agent`：发布 agent brief comment（[AGENT-BRIEF.md](AGENT-BRIEF.md)）。
   - `ready-for-human`：与 agent brief 相同结构，但注明无法委派的原因（判断事项、外部访问、设计决策、人工测试）。
   - `needs-info`：发布 triage 笔记（下方模板）。
   - `wontfix`：关闭 issue，comment 取决于*原因*：
     - **已实现**：改动已经存在。指出位置；**不要**写入 `.out-of-scope/`（该知识库用于*拒绝*请求，而非已建功能）。
     - **拒绝（bug）**：礼貌解释，然后关闭。
     - **拒绝（enhancement）**：写入 `.out-of-scope/`，comment 链接它，再关闭（[OUT-OF-SCOPE.md](OUT-OF-SCOPE.md)）。
   - `needs-triage`：应用角色。如果有部分进展，可选发 comment。

## Quick state override

维护者说“把 #42 移到 ready-for-agent”时，信任并直接应用角色。确认即将做的动作（角色变更、comment、关闭），再执行。跳过访谈。没有访谈却移到 `ready-for-agent` 时，询问是否希望编写 agent brief。

## Needs-info template

```markdown
## Triage Notes

**What we've established so far:**

- point 1
- point 2

**What we still need from you (@reporter):**

- question 1
- question 2
```

把访谈中已解决的全部内容记入“established so far”，避免丢失。问题必须具体且可行动，不能只说“请提供更多信息”。

## Resuming a previous session

issue 或 PR 已有 triage 笔记时，先阅读，检查报告者是否回答未决问题，继续前展示更新后的情况。不要重问已解决问题。
