将用户无法独自回答的事情转为一份 **questionnaire**：用户交给一个人异步填写，或在会议中共同填写的 Markdown 文档。接收者掌握用户缺少的知识；问卷负责把这些知识提取出来。

**追问发送目的，而非主题本身。** 只围绕用户肯定能回答的_发送_事项访谈：发给谁，以及需要对方返回什么。文档中的问题则针对接收者掌握的知识与用户需要的知识之间的 **gap**。


1. **发给谁？** 在一次交流中询问接收者的角色、专业知识及其与用户的关系。这决定问卷的语气和所需背景量。知道接收者是谁，以及对方掌握哪些用户不知道的知识，就算完成。

2. **需要对方返回什么？** 在一次交流中询问用户无法独自解决、需要此人回答的具体决策或事实。列出用户最终必须能够采取的行动或作出的决策，才算完成。

3. **编写问卷。** 针对步骤 1–2 的 gap 起草问题，遵循下方 Document structure。写入当前目录的 `to-questionnaire-<slug>.md`（slug 来自主题），并报告路径。文件存在且步骤 2 中用户列出的每项内容都有对应问题，才算完成。

## Document structure

将文档定位为 **discovery questionnaire**：用户缺少背景，接收者掌握背景。按重要性排列问题，因为异步交流可能只有一次机会；问题超过少量时，按主题用 `##` 标题分组。使用下方模板编写。

<questionnaire-template>

# <Questionnaire title>

**目的：** 为什么需要这份问卷，以及它影响哪个决策。

**发件人：** <用户>，**收件人：** <接收者>，**答案的用途：** <将用于何处>

## Context

用一段话帮助不在用户脑海中的接收者建立背景。足够支持高质量回答即可，不要写一整页。

## How to answer

说明截止时间和大致投入。部分回答和“不知道”也有用：标出不确定的事情，而不是跳过。

## <Theme heading>

每个主题一个 `##` 小节。各节中的问题按重要性排列。每个问题只表达一个想法，不合并多个问题，下面直接放回答占位；仅在问题容易被误解或敷衍回答时，加一句_为什么这很重要_。

<question-example>
### What load is the system expected to handle at launch?

_为什么这很重要：它决定我们现在为突发流量配置资源，还是稍后再做。_

>
</question-example>

## Anything else?

结尾留一个兜底问题：还有哪些我们没问、却应该知道的事情？

</questionnaire-template>
