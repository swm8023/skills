# 测试反模式

在新增或修改 mock、test double，或者考虑给生产代码添加仅供测试使用的 API 时读取本参考。

## 核心规则

1. 测试真实行为，不测试 mock 是否按预设工作。
2. 不要为了测试便利污染生产 API。
3. mock 前先理解真实依赖、数据结构和副作用。
4. 只隔离真正缓慢、不稳定或外部的边界；能使用真实组件时优先使用真实组件。

## 1. 测试 mock 而不是真实行为

错误信号：

- 断言 `*-mock` 元素存在。
- 主要断言只是某个 mock 被调用。
- 移除 mock 后，测试无法表达被测组件应有的行为。

错误示例：

```typescript
test('renders sidebar', () => {
  render(<Page />);
  expect(screen.getByTestId('sidebar-mock')).toBeInTheDocument();
});
```

应改为断言用户或调用方能观察到的真实结果，例如导航区域、输出值、状态变化或外部边界调用产生的业务效果。若必须隔离子组件，不要把“mock 存在”当成被测行为。

## 2. 给生产代码添加测试专用 API

添加生产方法前先问：

- 这个方法是否只会被测试调用？
- 当前类型是否真的拥有该资源或生命周期？
- 测试工具能否在生产类型外完成相同清理或搭建？

只供测试使用的清理、fixture 构造和状态注入应放在 test utilities。生产 API 只表达真实产品职责。

## 3. 未理解依赖就 mock

mock 一个方法前确认：

1. 真实方法有哪些返回值、状态变化和持久化副作用？
2. 当前测试是否依赖其中任何一项？
3. 能否在更低层只隔离网络、进程、时钟或其他外部操作？

如果高层方法同时承担业务状态更新和外部 I/O，不要整体 mock 掉它。优先保留业务逻辑，只替换最小外部边界。

## 4. 使用残缺 mock 数据

mock 响应必须符合真实契约，而不是只包含当前断言碰巧使用的字段。创建 mock 数据前查看实际类型、schema、文档或真实样本，并保留下游可能消费的字段。

无法说明真实结构时，不要凭猜测补一个部分对象；先确认契约，或使用项目已有 fixture/builder。

## 5. mock 复杂度掩盖设计问题

出现以下情况时停止继续叠加 mock：

- mock setup 比测试主体更长。
- 为让测试通过需要 mock 多层内部实现。
- 测试随着内部调用顺序变化而失败，但可观察行为没有变化。
- 无法解释每个 mock 隔离了什么风险。

此时优先考虑更窄的公共接口、依赖注入、项目已有测试 seam，或使用真实组件的集成测试。

## 提交前检查

- 断言是否描述真实可观察行为？
- mock 是否位于最小且正确的外部边界？
- mock 是否保留测试依赖的副作用和完整数据契约？
- 是否新增了只供测试调用的生产代码？
- 测试是否能在不过度依赖内部实现的情况下捕获回归？

如果任一项无法回答，先调整测试设计，再继续实现。
