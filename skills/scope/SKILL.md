# scope —— 把需求拷问清楚

## 概览
先快速理解项目当前状态，然后建立决策树，将未决策点逐题向用户拷问清楚，直到达成共同理解。

## 硬性关口

阶段 2 确认出口前，不允许调用实施类 skill，不允许写代码或执行其他实现动作；此前只允许必要的只读探索与 scope 所需的澄清、确认。

## 流程

### 阶段 1：探索与逐题澄清

#### 必要探索

理解用户意图，查阅相关代码，掌握当前实现、既有约束与行为边界。`docs/wiki/` 存在时，先扫描路径和首行摘要，再按需读取少量相关正文，以代码事实为准。

#### 决策梳理与收敛

根据用户目标和探索事实梳理决策点，决策点通常包含需求决策和技术决策，梳理完成后，按依赖关系组织成决策树。

- **需求决策**：明确要做什么、做成什么样，包括功能范围、使用流程、预期行为与结果，以及必须满足的约束和完成标准。
- **技术决策**：明确如何将需求落地为代码，包括实现方案、框架与技术选型、代码组织、模块与接口设计，以及关键实现流程。

内部维护已确认结论与未决点，复用用户已有确认。一次只问用户一个决策点，先需求后技术，优先询问前提明确、影响最高的未决点。

根据用户回答、新问题或要求更新决策树，补入未覆盖的决策点、调整依赖与收敛顺序，并排除不适用分支。前提变化或结论冲突时，复核受影响的决定；需要改动已确认结论时，与用户重新确认。

无未决点时，检查完成条件。

#### 核心规则

- **一次一题**。每条回复只问一个决策问题，等待用户回答后再推进。
- **优先多选题**。先梳理主要可行方案，再生成覆盖这些方案的选项，依次编号，附推荐和简短理由；无法提供合理选项时，使用开放题。
- **主动探索**。代码能解答的问题，先自己查证；无法解答时，向用户提问。可以看情况采用 subagent 进行并行探索。
- **不擅自揣测**。遇到无法由当前对话或代码事实唯一确定的内容、相互矛盾的结论或多种合理解释时，列为未决问题并交由用户决定。

#### 提问模板

普通 Markdown 选择题格式如下：

从 Q1 开始编号，每提出一个问题加 1，跨回复连续递增。`<n>` 替换为实际题号。

选项行按实际方案数量重复，依次使用 A、B、C……编号，每项单独成段。

```markdown
**Q<n> -** <问题正文，可分多段。>

<选项字母>. <选项说明>

推荐：<选项字母>，<简短理由>。
```


#### 完成条件

需求边界和技术决策中的所有适用项均已确认或不适用，形成设计视图和预估改动面所需事实已查明，且本次范围内无遗漏的未决问题或隐含假设后，进入阶段 2 做设计确认。

### 阶段 2：总结确认 + 出口选择

#### 设计确认

根据阶段 1 已确认的内容，简短呈现双方已经达成一致的目标、需求边界、技术方案，以及理解整体方案所必需的关键结构或流程。

设计呈现只用于暴露理解偏差，不要求达到 spec 的详细度；不展开完整验收证据、预估改动面、文件范围或实施步骤，除非它们会影响已确认决策。

呈现后按以下格式确认：

```markdown
确认以上理解并继续选择执行路径？
```

用户纠正需求边界或技术方案时，回到阶段 1 重新打开对应决策；仅修正表述时，在本阶段更新后重新呈现。

#### 出口选择

用户确认设计呈现后，根据已确认方案和预估改动面自行判断规模，不问用户：

- **小需求**：预估代码改动量足够小，通常只涉及一个局部行为和少量文件，不引入或改变架构、跨模块接口、数据结构、部署或迁移。
- **中大需求**：预估代码改动量较大，涉及多个行为或模块，或包含架构、接口、数据、部署、迁移等重大决策；必要探索后仍无法界定改动规模时按中大需求处理，不因尚未探索就直接升级。

按「wiki 落地判断」自行确定 wiki 目标，并在同一条消息中说明安排、确认执行路径：

```markdown
**wiki 更新：** <更新 path / 新建 path / 不更新 wiki>

请选择是否落 spec：

A. 落 spec —— 写入 `docs/scope/<日期>-<slug>.md`，批准后执行。

B. 不落 spec —— 在当前对话中生成实施契约；确认后执行，不生成 scope 或 plan 文档。

**推荐路径：** <A / B>，<简短理由>
```

默认依据此时的规模判断推荐路径：中大需求推荐 A，小需求推荐 B；有明确理由时可以偏离并说明原因。用户选择优先于推荐；用户确认路径后进入出口执行，wiki 目标无需单独确认。

#### 出口执行

正式契约只在用户选择路径后生成。以当前对话中的已确认结论和代码事实为依据，不把设计呈现当作完整契约来源。

验收由 AI 根据需求边界、技术决策和代码事实推导，不要求用户提供；如果推导过程中发现需要用户决定的实质需求或技术歧义，返回阶段 1。

**A. 落 spec**

1. 写 spec 文件前调用 `git-workflow` 的 `prepare` 阶段。
2. 写 `docs/scope/<YYYY-MM-DD>-<slug>.md`，按下文模板组织；`slug` 是根据主题生成的 kebab-case 英文短标题。
3. 按下文清单执行完整自我审查并就地修复。
4. 请用户审阅；审阅与修改期间沿用第 1 步建立的 Git 上下文。用户要求修改时，修改后重新完整自审；如果修改导致 wiki 更新目标变化，按「wiki 落地判断」自行调整。
5. 用户批准后，把 spec 头部状态回写为 `> 状态：已批准 <YYYY-MM-DD>`，再调用 `checkpoint` 只处理当前 spec。
6. 调用 `implement`，传入 `source_kind: approved-spec`、`source: <spec 路径>`、AI 确定的 wiki 目标和 `git_state: prepared`；implement 生成 plan 后直接执行，不再二次确认计划。

**B. 不落 spec**

1. 不写 spec 文件；参考下方 spec 模板及通用规则，在对话中生成其精简版，包含目标、决策基线、设计视图（功能设计、技术设计）、预估改动面和验收；只展开本次实施所需内容，关键结构或实现流程按需补充。
2. 按下文清单执行完整自我审查并就地修复。
3. 请用户确认实施契约。
4. 用户确认后调用 `implement`，传入 `source_kind: confirmed-conversation`、`source: <完整对话契约>`、AI 确定的 wiki 目标和 `git_state: unprepared`；不生成 `docs/scope/` 或 `docs/plans/` 文档，由 implement 直接规划并执行。

#### 完成条件

阶段 2 只允许两种出口：已确认对话契约交给 implement，或已批准 spec 交给 implement。

## wiki 落地判断

阶段 2 根据已确认方案与已有 wiki 自行确定目标，无需用户确认。复用已有探索，必要时扫描 `docs/wiki/` 路径与首行摘要，读取少量相关正文：

- **更新 `<path>`**：相关页面存在遗漏、过时或不准确。
- **新建 `<path>`**：有长期价值的新增知识无法由现有页面承载。
- **不更新 wiki**：无值得沉淀的变化，或已有内容已完整覆盖。

implement 在实现与验证完成后按实际结果复核目标并调用 wiki 同步；页面组织与写作遵循 wiki skill。

## spec.md 模板

spec 是 scope 与 implement 之间的设计基线，只保留约束实现或决定验收的结论，不记录访谈过程，也不提前展开 plan。

尖括号内容是字段说明，生成时替换并移除；标注“按需”的章节不适用时省略。

```markdown
> 由 scope skill 于 <YYYY-MM-DD> 生成
> 状态：待批准

# <主题>

## 目标
<用一段话说明当前问题和预期结果，不重复边界或方案>

## 决策基线

### 需求边界
<记录支持场景、正常与失败行为、明确不做及兼容要求；不讨论组件和文件>

### 技术决策
<记录职责、状态所有权、核心机制、接口、数据、存储、迁移、安全等 plan 不得自行改变的高阶结论；只为真实取舍保留必要理由>

## 设计视图

### 功能设计
<将需求边界综合为完整功能，说明入口、交互、状态、正常与失败行为及功能间关系；不逐条复述需求>

### 技术设计
<将技术决策综合为端到端实现方案，说明系统如何实现功能设计；足以指导 implement 细化实施，但不展开任务步骤>

#### 整体方案
<说明系统组成、组件职责、状态与数据所有权、接口边界、依赖关系及协作方式；存在跨模块拓扑、数据流、控制流或状态迁移时，可使用 Mermaid 图辅助，但图不代替关键职责和约束的文字说明>

#### 关键结构（按需）
<展开影响实现的数据模型、状态、接口或组件关系>

#### 实现流程
<从入口到结果写清主要调用、状态变化、异步处理、失败收敛和清理，形成全局实施指导而不是任务清单>

### 预估改动面
<按模块或目录说明预计变化、测试范围和 AI 确定的 wiki 目标；作为 implement 的探索起点，不是硬边界>

## 验收
<覆盖正常行为、重要失败场景和兼容性；逐项使用以下格式>
- <场景或约束 → 可观察结果；验证证据>
```

### 通用规则

- 每项结论只有一个权威定义；决策基线定义不可改变的需求边界和技术选择，设计视图负责将其综合为功能与技术方案，不引入未确认决策或与基线冲突。
- 以最少文字完整表达所有影响实现或验收的已确认结论；合并重复信息，不省略理解方案所需的背景、需求边界、技术选择、关键结构与流程、预估改动面和验收证据；不展开 plan 级任务拆分。

### 自我审查

1. **覆盖**：所有已确认需求和技术结论都有权威定义，并在功能设计、技术设计和验收中得到完整落实。
2. **分层**：决策基线定义边界与选择，功能设计说明功能如何工作，技术设计说明系统如何实现，验收验证最终结果；各层没有矛盾或重复定义。
3. **交接**：功能与技术设计足以让 implement 理解入口、职责、状态、流转、失败收敛和兼容边界，并据此细化文件和任务，无需重新决定核心实现方案。
4. **闭合**：验收均有可观察结果和验证证据，文档中不存在占位符、未决项或可产生两种理解的表述。

发现问题就地修复，通过后再交给用户审阅。
