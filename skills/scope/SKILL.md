# scope —— 把需求拷问清楚

## 概览
scope 分为三个阶段，必须严格按顺序执行；只有当前阶段达到完成条件，才能进入下一阶段。

## 硬性关口

在用户明确选择出口之前，**不要**调用任何实施类 skill、不要写代码、不要搭脚手架、不要做任何实现性动作。每一个进入 scope 的项目都适用，无论看起来多简单。

允许的前置动作只有三类：用户明确点名的元技能 / 审查技能、为回答事实问题所需的只读代码库探索（含 wiki 摘要预检）、scope 流程本身要求的澄清提问。它们不能转化为实现动作。`git-workflow-preferences` 只在阶段 3 选定出口后、首次准备写 spec、plan、wiki 或代码前以 `prepare` 阶段使用；纯澄清阶段最多读取已存在的 `docs/user/git-preferences.md` 作为约束，不初始化偏好文件。

## 流程

### 阶段 1：判断规模 + wiki 摘要预检 + 探索

自己判断"小需求"还是"中大需求"，不问用户：

- **小需求**（边界清晰、单文件级、明显简单）—— 跳过探索，直接进入阶段 2
- **中大需求**（多文件、影响范围不确定、涉及架构 / 接口 / 新模块）—— 如果需要探索代码，先扫 `docs/wiki/` 的文件路径和每个 `.md` 的第一行摘要，看是否有相关项目知识；只看摘要，不读正文。然后做主题相关的代码库快速探索（30 秒级别）：grep / glob 关键词、读最相关的几个文件、查相关 commit。**不做无关探索**

小需求若已经边界清晰，阶段 2 只核对已有结论并补齐账本，不为了形式再做代码库扫描或技术访谈；若仍缺少产品决策，按普通阶段 2 逐题收敛。

拷问中遇到事实问题（"仓库里有没有 X"），自己去查，不扔给用户。wiki 摘要只用于定位上下文和收窄探索，不能代替代码事实验证。

完成规模判断以及必要的 wiki 摘要预检和代码探索后，阶段 1 完成。

### 阶段 2：拷问式连续提问

进入阶段 2 时维护内部**决策账本**，跟踪目标、需求边界、技术决策、验收与验证；每项标记为“已确认”“待决策”或“不适用”。账本只用于防遗漏，不直接抄入实施契约或 spec。

每次用户回答后先更新账本，再从待决策项中选择影响最高的一项；不要重问已确认内容，也不要为了填满清单而追问“不适用”项。若进入 scope 时所有适用项已经闭合，只核对账本，不重新发起访谈；用户推翻已确认决策时，重新打开对应项。

先收敛需求，再收敛技术落地：

- **需求收敛**：明确目标、支持与排除边界、可观察行为、失败行为和成功标准。
- **技术收敛**：基于已确认需求做针对性只读探索，只确认影响职责、架构、接口、数据、部署、迁移、安全或兼容性的高阶技术决策；局部实现细节留给 do-scoped。

技术方案与已确认需求冲突时，回到需求问题重新确认。

核心规则：

- **一次一题**。同一条消息塞多个问题会让用户挑容易答的、回避难的。
- **每题给推荐答案**。让用户审核而不是白板思考。
- **决策树式深挖**。A 的回答决定下一题问 B 还是 B'。
- **代码库能答的不问用户**。
- **优先多选题**（A/B/C + 推荐），开放式次之。
- **选项之间空一行**，确保每个选项是独立 Markdown 段落。
- **关注目的、约束、成功标准**。需求问题不问实现方式；技术问题只问存在实质取舍的落地方案。

账本中不存在适用的待决策项时，阶段 2 完成。

### 阶段 3：总结确认 + 出口选择

只有账本中的所有适用项都闭合，才能进入本阶段。进入后做简短的统一设计呈现，询问用户是否正确；如果用户纠偏，回到阶段 2 重新打开对应项。

用户确认理解一致后，按「wiki 落地判断」生成 wiki 建议，并在同一条消息里确认出口和 wiki 目标：

> "下一步走哪条路径？
>
> - **落 spec** —— 我会写 `docs/scope/<日期>-<slug>.md`；你批准后，把 spec 和已确认的 wiki 目标交给 do-scoped，由它生成持久化 plan 并直接执行
> - **不落 spec** —— 我直接在对话里生成实施契约；你确认后，把契约和已确认的 wiki 目标交给 do-scoped 执行（不生成 scope/plan 文档；契约只存在于本次对话，会话中断即丢失，建议确认后直接执行）"

同一条消息中必须列出：

- **推荐路径**：落 spec / 不落 spec。默认沿用阶段 1 的规模判断：中大需求推荐落 spec，小需求推荐不落 spec；有明确理由时偏离并说明，用户的选择优先于推荐。
- **wiki 更新建议**：`更新 <path>`、`新建 <path>` 或 `不更新 wiki`。
- **待用户确认**：路径是否接受、wiki 目标是否接受。

统一设计呈现必须能直接映射到同一份实施契约：目标、决策基线（需求边界与技术决策）、设计视图、预估改动面、验收与验证、wiki 目标。若其中仍有“待定”或两种可行解释，不能进入出口选择，回到阶段 2；如果都已闭合，才询问路径和 wiki 目标。

#### 只给计划路径

- 用户已经明确要求“不执行、只给计划”时，不再询问落 spec / 不落 spec；在对话中生成实施计划后停止
- 不写 `docs/scope/`、`docs/plans/` 或其他仓库文件，不调用 do-scoped，不执行实现
- 计划仍以已确认的目标、决策基线、设计视图和验收为输入，精确到足以交给后续执行者

#### 不落 spec 路径

- 对话里直接生成与 spec 同构的实施契约：目标、决策基线、必要的设计视图、预估改动面、验收与验证
- 立刻做快速自我审查：决策是否无遗漏且各有唯一归属、设计是否足以指导实施、验收是否可验证
- 用户确认后调用 `do-scoped`，传入 `source_kind: confirmed-conversation`、完整契约和已确认的 wiki 目标
- 不生成 `docs/scope/` 或 `docs/plans/` 文档；由 do-scoped 建立对话 Todo、同步 wiki（如需要）、执行并负责 Git 全生命周期

#### 落 spec 路径

1. 写 spec 文件前调用 `git-workflow-preferences` 的 `prepare` 阶段
2. 写 `docs/scope/<YYYY-MM-DD>-<slug>.md`，按下文模板组织；`slug` 是根据主题生成的 kebab-case 英文短标题
3. 立刻做自我审查（4 项检查），就地修复
4. 请用户审阅
5. 用户要求修改就改并重跑自我审查；如果修改导致 wiki 更新目标变化，先向用户确认新的 wiki 文件
6. 用户批准 spec 后，先把 spec 头部状态回写为 `> 状态：已批准 <YYYY-MM-DD>`，再调用 `do-scoped`，传入 `source_kind: approved-spec`、spec 路径和已确认的 wiki 目标：
   > "我正在使用 do-scoped skill 来规划并完成这个已批准的 spec。"

   do-scoped 在 `docs/plans/<spec 文件 basename>/` 中生成一个或多个 `plan-*.md`，自我审查后直接执行，不再要求用户另行调用执行 skill。

   spec 的预估改动面只为 do-scoped 提供代码探索起点，不是精确文件清单或 plan 的硬边界。do-scoped 可以依据代码事实自行细化文件与任务，不需要二次确认；只有实施需要改变需求边界、技术决策、验收或引入新的实质风险时，才回到用户决策。

**终止状态：** 要么"只给计划 → 对话中输出后停止"，要么"已确认对话契约 → do-scoped"，要么"已批准 spec → do-scoped"。

### Git 所有权与 handoff

- scope 一旦写入 spec 或其他仓库文件，就持有本阶段的 Git 所有权。首次写入前必须已有 `prepare` 结果。
- 每次在持久化修改后暂停等待用户、结束本轮或 handoff 前，都调用 `finalize`，并传入 `complete`、`awaiting_review` 或其他真实任务结果。
- handoff 给 do-scoped 前完成自己的 `finalize`；不传递 Git 状态——do-scoped 会重新执行 `prepare`、核对仓库事实并建立本次执行的文件所有权，交还控制权前调用自己的 `finalize`。
- 不落 spec 路径在 scope 阶段不写仓库，由 do-scoped 负责 wiki、实现和 Git 全生命周期。

## wiki 落地判断

离开 scope、进入 do-scoped 前，必须完成 wiki 落地判断；这个判断不以是否落 spec 为前提。

- **扫描方式**：只读 `docs/wiki/` 路径和每个 `.md` 第一行摘要，不读正文。
- **确认时机**：阶段 3 询问是否落 spec 时，同时让用户确认 wiki 目标；把结果作为 do-scoped 输入，后续只同步用户确认过的文件。
- **建议类型**：`更新 <path>`、`新建 <path>`、`不更新 wiki`。
- **落 spec**：大任务默认建议同步 wiki。可更新已有页面；也可在用户确认后新建最小必要目录或页面。
- **不落 spec**：小任务只建议更新已有 wiki；没有匹配页面时不新建，除非用户明确要求沉淀。
- **可写入内容**：已确认的架构、约定、术语、稳定流程、模块背景、决策背景。
- **不可写入内容**：未确认猜测、一次性任务步骤、执行 checklist、对话过程。

阶段 3 生成建议前必须先完成上述摘要扫描；没有匹配页面时，小任务默认“不更新 wiki”，中大任务才可建议在用户确认后新建最小必要页面。不要把“建议更新”当成用户已经授权。

wiki 同步是 do-scoped 的第一个实施工作单元，不改变 scope 出口。落 spec 路径仍在写 spec 前执行 Git `prepare` 并在等待批准前 `finalize`；不落 spec 路径由 do-scoped 在首次写入前执行 Git `prepare`。

## spec.md 模板

spec 是 scope 与 do-scoped 之间的设计基线：保留会约束实现或决定验收的结论，既不抄录访谈，也不提前展开 plan。一级标题是主题名，正文使用以下四个二级章节：

```markdown
> 由 scope skill 于 <YYYY-MM-DD> 生成
> 状态：待批准

# <主题>

## 目标

## 决策基线

### 需求边界

### 技术决策

## 设计视图

### 系统结构（按需）

### 关键结构（按需）

### 关键流程（按需）

### 预估改动面

## 验收
```

### 目标

用一段话说明当前问题、预期结果和用户价值，只写 before / after，不在这里重复边界或方案。

### 决策基线

使用两个三级小节：

- **`### 需求边界`**：记录支持对象与场景、可观察的正常和失败行为、明确不做、必须保持的兼容行为。它描述产品不变量，不讨论组件和文件。
- **`### 技术决策`**：记录职责与状态所有权、核心机制、接口、数据、存储、部署、迁移、安全、故障隔离等后续 plan 不得自行改变的高阶结论。只在存在真实取舍时保留必要理由，不写废弃备选。

### 设计视图

先用一段话或一张简图把决策组织成整体方案。系统结构、关键结构和关键流程按实际复杂度选择，没有实质内容的直接省略；预估改动面保留，作为 do-scoped 的实施交接：

- **`### 系统结构`**：组件、职责、依赖和边界。写关系，不重复技术决策结论。
- **`### 关键结构`**：跨任务必须保持一致的 API、事件、配置、数据模型、状态机或持久化格式；需要时直接给最小结构样例。
- **`### 关键流程`**：正常路径，以及会影响设计的失败、恢复、并发或迁移路径。
- **`### 预估改动面`**：按模块或目录说明预计变化及职责，包含测试和已确认的 wiki 目标；不穷举文件，不写任务顺序。它是 do-scoped 的探索起点，不是硬边界。

### 验收

使用编号或项目符号逐项写明“场景或约束 → 可观察结果；验证证据”。覆盖正常行为、重要失败场景和必须保持的兼容性；证据可以是自动化测试、构建、静态检查或必要的人工检查。只写完成标准，不复述方案或实现步骤。

元信息按骨架写入。用户批准后把状态回写为 `> 状态：已批准 <YYYY-MM-DD>`——批准状态以 spec 文件为准，不以对话记忆为准，do-scoped 凭状态行判断 spec 是否可执行。

**写作风格：**
- **简洁优先**，没必要的不写。
- **一个事实一个权威位置**：决策写约束，设计写关系，验收写证据；不要跨节复述同一含义。
- **高层压缩而非删减**：所有已确认需求和技术结论都要保留，但访谈过程、废弃备选、精确文件和执行步骤不写。
- **按需展开设计视图**：没有关键结构或显著流程时省略对应三级小节，不为模板凑字。

写完 spec 后立刻过一遍：

1. **决策覆盖：** 对照决策账本，每项已确认的需求或技术结论是否恰好出现一次；有遗漏就补，有重复就保留唯一权威位置。
2. **层次与一致性：** 需求边界、技术决策和设计视图是否各司其职且互不矛盾；设计是否足以让 do-scoped 理解入口、职责、状态、流转、失败收敛和兼容边界。
3. **验收证据：** 每项验收是否有可观察结果和验证证据，是否覆盖关键失败行为与兼容性。
4. **任务边界：** spec 是否聚焦于一个连贯、可整体验收的结果；允许 do-scoped 拆成多个 plan，只有独立价值或独立批准边界才拆 spec。
5. **占位符与歧义：** 扫描 "TBD"、"TODO"、"implement later"、"待定"、"待确认"、"适当处理" 等未决或空泛措辞；任何能被解读成两种意思的需求都先明确。

就地修复，无需再做自我审查，修完继续。
