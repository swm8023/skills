# write-doc

## 写作委托

从本次请求和允许访问的材料中明确读者、写作目标、事实依据、编辑范围和交付要求。可比较授权范围内的同目录文档；资料缺口影响成稿时再向调用方澄清。各阶段沿用同一份委托，按用户指定的范围和形式交付。

## 流程

1. **读取写作参考。** 先读 [write-technical](references/write-technical.md)，再读 [write-zh](references/write-zh.md)，根据读者目标和文稿用途组织内容。
2. **起草正文与图示。** 以已确认材料为依据，按授权范围形成稿件。需要图示时，读 [Mermaid](references/mermaid-diagrams/index.md) 及对应图类型的参考，将图与正文一起组织。
3. **子代理优化。** 保留优化前稿件，将允许披露的稿件或授权文件路径、受众、编辑范围和必要材料交给子代理，按 [optimize-zh](references/optimize-zh.md) 优化。等待其完成后，对照核查事实、限定和受保护内容；同一文稿的修改按顺序进行。
4. **独立子代理复核。** 由未参与起草和优化的只读子代理按 [review-doc](references/review-doc.md) 检查成稿质量和流程证据。处理有依据的问题，实质修改后复查受影响内容。
5. **交付。** 返回用户要求的正文、文件修改或审阅意见，供调用方完成后续写入或发布。复核记录留在任务内部，仅说明影响交付的未解决问题或证据缺口。

子代理仅执行受委托的阶段，读取范围限于交接材料、授权路径和所需参考；优化阶段的文件修改遵守本次授权。Git 工作流和最终交付由主代理负责。子代理不可用时，由主代理完成对应阶段并如实说明执行方式。
